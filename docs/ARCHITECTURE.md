# AppLocker — Technical Architecture

This document maps the repository layout, runtime architecture, data flows, integrations, and known technical debt. It reflects the codebase as of the current `main` branch.

## 1. Repository layout

| Path | Role |
|------|------|
| `Sources/AppLocker/` | Single SwiftPM executable target; shared code for macOS and iOS |
| `Sources/AppLocker/MacAppLockerApp.swift`, `MacContentView.swift`, … | macOS-only entry and UI (guarded or excluded from iOS in Xcode) |
| `Sources/AppLocker/iOS/` | iOS companion (`AppLockerCompanion`) entry, tabs, feature UIs |
| `Sources/AppLocker/Shared/` | Cross-platform models, crypto, CloudKit, sync, logging |
| `SupportingFiles/macOS/`, `SupportingFiles/iOS/` | Info.plist, entitlements per target |
| `Sources/AppLocker/Assets.xcassets/` | Shared asset catalog (App Icon for both targets) |
| `AppLocker.xcodeproj/` | Generated by **XcodeGen** from `project.yml` |
| `Package.swift` | SwiftPM: `AppLocker` library/executable + `AppLockerTests` |
| `Tests/AppLockerTests/` | Unit tests (models, crypto, schedules, sync, CloudKit helpers) |
| `scripts/` | Release, signing, App Store export |
| `docs/plans/` | Historical design/implementation notes (not executable specs) |

**Dual build systems:** Day-to-day app builds use **Xcode** (`project.yml` → `xcodebuild`). **SwiftPM** (`swift build` / `swift test`) compiles the same sources with `SWIFT_PACKAGE` for CI-friendly tests; the iOS `@main` entry is still compiled on macOS for the host SDK where applicable.

## 2. Targets and modular boundaries

| Target | Platform | Bundle ID (from `project.yml`) | Purpose |
|--------|----------|----------------------------------|---------|
| **AppLocker** | macOS 13+ | `com.mirxa.AppLocker` | Primary app: monitor/block apps, vault, quotas, focus, notifications, CloudKit + KV sync |
| **AppLockerCompanion** | iOS 16+ | (see `project.yml` — `AppLockerCompanion`) | Dashboard, remote commands, alerts, secure notes read/sync, Family Controls–related surfaces |

**Source exclusion:** macOS target excludes `Sources/AppLocker/iOS/**` from compilation; iOS target pulls `iOS/`, `Shared/`, and selected top-level files (e.g. `NotificationManager.swift`).

**Modular pattern:** Singleton-style `@MainActor` managers (`AppMonitor`, `AuthenticationManager`, `CloudKitManager`, `KVStoreManager` (iOS), etc.) plus SwiftUI views. Shared types live in `Shared/Models.swift` and related files.

## 3. Coding conventions (observed)

- **Swift 5.9**, SwiftUI-first UI; macOS uses AppKit where needed (alerts, menu bar, window delegate).
- **Platform guards:** `#if os(macOS)` / `#if os(iOS)` / `#if targetEnvironment(simulator)` for capabilities that differ (e.g. CloudKit entitlement detection on simulator).
- **Logging:** `OSLog` via `AppLogger` categories (`app`, `crypto`, `notifications`, `intruder`, `cloud`).
- **Persistence:** `UserDefaults` for non-sensitive preferences; **Keychain** for passcodes, salts, HMAC secret, failed-attempt counters; file-based storage for vault and encrypted exports.
- **Concurrency:** `async`/`await` for CloudKit; `Task { @MainActor in ... }` for UI-bound work.

## 4. Dependency chain (internal)

```
User / OS
  → Mac: NSWorkspace + polling → AppMonitor → terminate / show unlock UI
  → AuthenticationManager (passcode, biometrics, lockout)
  → NotificationManager (local + NSUbiquitousKeyValueStore + RemoteCommand HMAC)
  → CloudKitManager (private DB: events, locked-app list assets)
  → IntruderManager / SecureNotes / Vault / … (feature modules)
```

**iOS companion:** `KVStoreManager` decodes Mac-written keys from **iCloud Key-Value Store**; `CloudKitManager` fetches records where applicable (e.g. intruder photos). Remote control signs commands with the same HMAC scheme as macOS verification.

## 5. Third-party and Apple integrations

| Integration | Usage |
|-------------|--------|
| **CloudKit** | Private database: blocked/failed events, locked-app JSON assets, push subscriptions |
| **APNs** | Device registration for CloudKit push; handlers refresh account + KV (iOS) |
| **NSUbiquitousKeyValueStore** | Cross-device alerts, remote commands, locked app list mirror, secure notes envelope |
| **LocalAuthentication** | Touch ID / Face ID / device-owner policies |
| **CryptoKit + CommonCrypto** | AES-GCM, SHA256, HMAC, PBKDF2 (via `PBKDF2Helper` / `CryptoHelper`) |
| **UserNotifications** | Local notifications, categories, delegates |
| **Family Controls** (entitlements) | iOS companion capabilities (see `AppLockerCompanion.entitlements`) |

There are **no CocoaPods/SPM third-party runtime dependencies** in `Package.swift`.

## 6. Core operational workflows

### 6.1 macOS — Block locked app

1. User enables monitoring → `AppMonitor.startMonitoring()` (workspace notifications + ~200ms poll).
2. Running app matches `LockedAppInfo` → unless schedule allows or temporarily unlocked → `terminateApp`.
3. Notifications + optional CloudKit publish + usage records + unlock UI.

### 6.2 Cross-device alert

1. Mac writes `com.applocker.latestAlert` to ubiquitous KV.
2. Other devices observe `NSUbiquitousKeyValueStore.didChangeExternallyNotification` → local notification.

### 6.3 Remote command (iOS → Mac)

1. iOS signs `RemoteCommand` with Keychain-stored symmetric secret (`CommandSigner`).
2. Command written to KV; Mac `NotificationManager.iCloudKVChanged` verifies HMAC, posts `RemoteCommandReceived`.
3. `AppMonitor.handleRemoteCommand` applies lock/unlock (clears temporary unlocks on lock-all, screen lock shortcut + fallback).

### 6.4 Passcode lifecycle

- New passcodes use **PBKDF2** (v2) with Keychain-stored version flag; legacy v1 (single SHA-256 step) verified on login and upgraded on success.

## 7. UI hierarchies (summary)

- **macOS:** `MacAppLockerApp` → `WindowGroup` → `MacContentView` (tabbed main UI), `NSStatusItem` menu, `AppDelegate` for notifications, iCloud KV, window/quit policy.
- **iOS:** `iOSAppLockerApp` → `iOSRootView` → lock overlay or `TabView` (`DashboardView`, locking, hiding, secure notes, remote control, settings, etc.) — see `iOSContentView.swift` for full tab list.

## 8. Persistent storage map

| Data | Storage |
|------|---------|
| Locked apps, categories, usage, settings | `UserDefaults` / encoded Data |
| Passcode hash, salt, version, lockout, HMAC secret | Keychain |
| Vault / file locker | App sandbox files + metadata in UserDefaults or sidecar |
| Secure notes sync | Encrypted payloads in KV + optional CloudKit-related paths on Mac |
| Notification history | UserDefaults |
| Export backup | Optional encrypted `.aplockerbackup` (custom APLK envelope) |

## 9. Testing

- **SwiftPM:** `swift test` — model/crypto/schedule/sync/CloudKit notification smoke tests.
- **Not covered in CI by default:** UI tests, XCUITest, on-device Family Controls, full CloudKit E2E (requires Apple ID + container).

## 10. Technical debt and risks (honest)

| Area | Notes |
|------|--------|
| **README vs code** | User-facing README historically mentioned SHA-256-only passcodes; implementation uses PBKDF2 v2 with migration — keep docs in sync. |
| **Xcode vs provisioning** | iCloud container must match Developer Portal + provisioning profiles; local `xcodebuild` may fail until profiles align. |
| **Simulator** | iOS Simulator: CloudKit may be disabled by code paths (`hasCloudKitEntitlement` false); test on device for full stack. |
| **Accessibility / Apple Events** | Lock screen uses System Events / workspace patterns that require user-granted permissions and may fail silently — errors are logged where possible. |
| **Plan docs** | `docs/plans/*.md` are planning artifacts; they are not automatically kept in sync with code. |
| **SwiftPM vs Xcode** | `@main` exists in both platform files; ensure Xcode target membership matches intended platform. |

## 11. Release and signing

- **Unsigned / ad-hoc:** `make release` → `scripts/build-release.sh` (see `RELEASE.md`).
- **Developer ID / notarization / App Store:** `scripts/release-signed.sh`, `scripts/publish-appstore.sh` with environment variables documented in `RELEASE.md`.

**Signed distributable binaries** are produced on a machine with valid Apple certificates and team membership; they cannot be generated meaningfully inside a generic CI sandbox without those secrets.

## 12. Asset icons

App icon PNGs live under `Sources/AppLocker/Assets.xcassets/AppIcon.appiconset/`. To regenerate from a new master image, use `scripts/generate-app-icons.sh` (see script header) or replace assets manually in Xcode.
